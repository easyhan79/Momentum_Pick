# Telegram 테스트 접수 무응답 진단

2026-11-06 (한국시간). 사용자가 테스트 매물을 보냈으나 텔레그램 접수 안내가 없다고 보고했다.

## 현재까지 확인한 사실

- 클라우드 작업 환경 오류 후 실행 연결이 복구되어 직접 조회를 재개했다.
- 분석 작업 #38(`42183211581`)은 main 코드 `0df962c579d538ecf01cb1f9ebcd124c53e67be0`로 성공했다. 하지만 예약 실행 성공만으로 이번 테스트 매물의 처리 성공을 확인할 수는 없다. 상세 실행 로그는 비로그인 조회로 볼 수 없었다.
- 별도 `audit/telegram-intake-20261106` 브랜치의 읽기 전용 진단을 GitHub Actions에서 실행했다. 기존 Secrets를 정상적인 API 인증으로 사용했으며 토큰·원본 URL·사용자명·고객 원문/ID/정확한 건수를 출력하지 않는다. 고객 데이터, 작업 대기열, Webhook을 변경하거나 메시지를 보내지 않았다.
- 최신 진단 실행: `42191794440`. 봇 인증 정상, 일반 message 업데이트 수신 활성화, 대기 중 Telegram 업데이트 없음, 최근 Webhook 오류 기록 없음.
- 등록된 Webhook은 같은 Supabase 프로젝트의 같은 `clever-endpoint`이다. 처음에는 전체 URL 문자열이 일치하지 않아 다른 주소로 분류했지만, 추가 검사로 URL 부가옵션 차이임을 확인했다. 이를 근거 없이 잘못된 Webhook으로 단정하거나 URL을 덮어쓰지 않았다.
- 기존 GitHub 서버 credential로 Supabase DB 접근은 정상이다. 예상 health URL과 기존 Webhook URL에 대한 인증 GET은 HTTP 401(plain Unauthorized)이다. 이는 진단용 GET의 거절이며 Telegram POST도 401이라고 단정할 수 없다.
- 최근 24시간 내 raw_input에 ‘테스트’가 포함된 매물은 조회되지 않았다. 사용자가 실제 입력에 그 표시를 넣었는지는 아직 답변을 받지 못했으므로 이번 입력이 절대 저장되지 않았다고 단정하지 않는다.
- 진단한 봇은 그룹 개인정보 보호 모드가 켜져 있다. 그룹에서 관리자 권한/멘션 없이 보낸 일반 메시지는 전달되지 않을 수 있다. 개인 대화 여부와 실제 입력한 봇의 @아이디를 확인해야 한다. 봇 이름은 출력하지 않고 지문으로만 대조한다.
- GitHub의 SUPABASE_ACCESS_TOKEN 바인딩은 없다. 서비스 DB key를 관리 API 권한으로 취급하지 않는다.
